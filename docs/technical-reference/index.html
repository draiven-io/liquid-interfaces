Liquid Interfaces

A protocol for agent systems where the interface is an event, not an artifact

Integration has always assumed that System A must know, in advance and to the byte, what System B expects. Autonomous agents break that assumption from both ends. Liquid Interfaces removes form as a precondition for interaction, and replaces it with intent, negotiation, and dissolution.

01

The problem it solves

The history of integration is the history of imposing predictability. RPC, SOAP, REST, GraphQL — different syntax, one premise: the caller must know the callee's shape in advance, exactly.

That premise held because callers were deterministic programs written by people who could read documentation. It stops holding when the caller is an autonomous agent, because the two sides now disagree about what an interaction is.

The agentThe API
Operates probabilisticallyOperates deterministically
Interprets natural languageRequires rigid syntax
Adapts to ambiguous contextDemands a fixed schema
Pursues goals — “reduce logistics cost”Executes functions — POST /orders/v1

The industry's answer has been to translate: hand-written connectors, tool descriptions, function-calling schemas. That works, and it produces a specific kind of debt. Every integration is a permanent artefact someone maintains. Every schema change is a breaking change somewhere. The cost does not scale with value delivered; it scales with the number of pairs of things that talk.

The observation LIP starts from

When two agents collaborate, the interface between them exists for the duration of one interaction and then has no further purpose. Persisting it — as a connector, a schema, a client library — is not free. It is the thing you will migrate later.

The core claim

If an interface only needs to exist while an interaction is happening, then making it durable is a cost with no corresponding benefit. Liquid Interfaces makes the interface ephemeral by construction: it is negotiated when needed and dissolved when finished, leaving nothing to maintain.

This is not an argument that types are bad or that validation is optional. It is an argument about when the contract is established. LIP establishes it at interaction time, from what the participants declare about themselves, rather than at design time from what someone anticipated.

02

The protocol

LIP is a message protocol. Every message is a JSON envelope with a performative — an act that changes the state of an interaction. The set of performatives is closed.

2.1 The envelope

Identical for every message type. The payload varies; the frame does not.

{
  "protocol_version": "0.3.0",
  "message_id":       "0d6f2f1e-1b4a-4c62-9f6a-2c0f0c9a1d33",
  "session_id":       "9d1f7c02-...",   // the interaction context
  "message_type":     "offer",          // the performative
  "timestamp":        "2026-08-22T14:48:55+00:00",
  "sender": {
    "kind": "agent",                    // requester | coordinator | agent
    "id":   "route-optimizer-01",
    "oidc_subject": "..."
  },
  "trace": { "trace_id": "...", "span_id": "..." },
  "payload": { /* shape determined by message_type */ }
}
Why sender.id is not identity

sender.id is written by the sender. It is a claim. A coordinator that authorises on it has authorised whatever the caller typed. Section 4.4 covers what LIP does instead.

2.2 The ten performatives

Closed by design. Adding one changes what the protocol means, which is what the RFC process exists for. In a typed implementation this becomes a finite union rather than a string, and the compiler enforces it.

PerformativeDirectionEffect
registerAgent → CoordinatorDeclares the agent and the capabilities it offers
registeredCoordinator → AgentAdmits or refuses that declaration, with a reason
intentRequester → Coordinator
Coordinator → Agent		Articulates an objective; relayed to candidate agents
offerAgent → CoordinatorDeclares a capability relevant to the intent
acceptCoordinator → AgentSignals negotiated agreement
rejectCoordinator → AgentStructured refusal, with cause
executeCoordinator → AgentAuthorises work under negotiated terms
completeAgent → CoordinatorTerminates execution, successfully or not
dissolveCoordinator → AllInvalidates the context; mandatory cleanup
eventAny → AnyInformational progress; changes no state

2.3 The lifecycle

2.4 Registration is per connection

An agent registers on every connection, including reconnections. The coordinator holds its capability registry against the live channel, so an agent that reconnects without registering is connected and undiscoverable — healthy to a process supervisor, absent from the bus.

This is the failure mode RFC 0001 was written to eliminate. Before it, agents registered by sending complete with the sentinel session_id="__registration__"; registration could not fail visibly, and an agent refused admission stayed connected believing it was live.

2.5 Versioning

Every message carries protocol_version. A message without one is treated as 0.1.0 — the last version predating the field — rather than as current. Compatibility is not symmetric, and saying so plainly matters more than the version number:

AgentCoordinatorResult
0.2.00.2.0Full handshake
0.1.00.2.0Works — the deprecated form is still accepted
0.2.00.1.0Agent never registers — the coordinator ignores register
0.3.00.2.0Works — the agent is told nothing about grants, and no artifact is validated
0.2.00.3.0Works — declared scopes are read as requests

Coordinators are upgraded before agents. This is the usual ordering for a client/server protocol, but it is a real operational constraint rather than a formality.

03

Dissolution and the anti-debt principle

This is the part of LIP that is genuinely unusual, and the part most worth defending, because it is where the protocol makes a claim no other agent protocol makes.

A conventional contract persists. That is its purpose: it is a promise about the future. The cost is that it must be maintained, versioned, deprecated and migrated — and it constrains interactions nobody has had yet.

A LIP contract is designed to dissolve. It has limited temporal validity, exists only inside a session, and is invalidated by dissolve, which triggers mandatory cleanup across every participant.

Invariant II

Nothing outlives the interaction that created it. When a session dissolves, the negotiated contract, the execution plan, the session memory and the agent bindings are all discarded. What remains is the audit record of what happened — deliberately not the machinery that made it happen.

3.1 What this buys

  • No connector inventory. Adding an agent means registering capabilities, not editing another agent.
  • No breaking changes between agents. There is no persistent contract to break; the next negotiation reflects the current declarations.
  • Bounded blast radius. An interaction that goes wrong is dissolved. It cannot leave a half-configured integration behind.

3.2 What it costs, honestly

  • Every interaction pays negotiation cost. Discovery and planning are real work, and for a hot path called ten thousand times a second they are the wrong trade. LIP is for coordination, not for the inner loop.
  • Reproducibility takes deliberate effort. If the plan is composed at runtime, "why did it do that" is answerable only if you recorded it. Hence the audit trail is not optional in the reference implementation.

3.3 Dissolution during execution

An agent may have work in flight when dissolve arrives. The specification requires it to stop, and to not send complete afterwards: the interaction context the completion would report against no longer exists. Two conformant implementations behaving differently here is precisely the ambiguity a specification exists to prevent, so it is stated explicitly.

04

IBAC — Intent-Based Access Control

The strongest independent criticism of agent protocols is not that they are slow or immature. It is that they cannot express purpose, delegation, revocation or provenance — so authorisation stays at the endpoint while the decision that mattered was made somewhere else. IBAC is the answer to that criticism.

4.1 Why RBAC and ABAC do not fit

ModelAuthorisesWhy it is insufficient here
RBACA role calling an endpointAn agent's role is stable; its purpose changes every request. The same agent legitimately reading customer records for a support query is exfiltrating when the purpose is different.
ABACAttributes of subject, object, environmentCloser — but the attribute that decides this case is why, and “why” is not an attribute of the subject or the object. It is a property of the interaction.
IBACThe intent behind the request, at every stage of itEvaluates the interaction rather than the call. The same endpoint, the same identity, the same data — different answers, because the purpose differs.

4.2 Five evaluation points

A request is not judged once. It is judged five times, each against what is known by then — because what is knowable changes as the interaction proceeds.

4.3 Three layers, ANDed

Each evaluation runs three layers, and the strictest decision wins. The layers are combined, never short-circuited: any layer must be able to block what another approved, and that guarantee is worth nothing if one ALLOW ends the evaluation.

That property is worth stating precisely, because it is the answer to the most serious objection to putting a language model anywhere near authorisation. The precedence order is DENY → REQUIRE_HUMAN_APPROVAL → ALLOW_WITH_SCOPE → ALLOW, and the combiner selects the minimum. A compromised or confused model can refuse things it should have permitted. It cannot permit things it should have refused.

4.4 Declared versus derived

Every fact entering an IBAC evaluation is classified, and the classification decides which rules can carry a guarantee.

Declared — the actor wrote itDerived — the coordinator established it
intent_text, purpose, context, claimed_agent_id authenticated_subject, authenticated_agent_id, identity_verified, session_id, evaluation_point
Can be reworded until it passes. A rule reading only declared input is a heuristic, however well written. Resolved from the authenticated connection and the coordinator's own state. Cannot be argued away by phrasing the request differently.
Why this distinction is load-bearing

The invariant layer reads only derived facts. That is what lets it carry a guarantee. A result is marked relies_on_declared_input when the deciding layer read something the actor asserted — so an operator can tell which of their controls are boundaries and which are merely good defaults.

The concrete attack this closes: an agent putting a colleague's identifier in sender.id. The manifest compares the claim against the identity resolved from the connection, and impersonation becomes a detectable, attributable event rather than a successful one.

4.5 Fail-closed

Policy

An evaluation that did not happen is not permission. If the semantic layer cannot reach its model, the decision is DENY — not “fall back to the deterministic rules and continue”.

This is a deliberate posture with a real cost: a model outage stops work that would otherwise have been permitted. It is chosen because the alternative is worse, and because the alternative is what systems drift into by default. Fail-open authorisation is rarely designed; it accumulates, one exception handler at a time, and it is invisible until the day it matters.

4.6 Bounded capabilities

An approval that grants nothing specific has approved everything. When IBAC allows, it issues a capability — a bounded, expiring grant naming exactly what may be done.

PropertyMeaning
principalWho holds it — the authenticated subject, not a claimed id
scopesExactly what it permits; anything outside is denied
expires_atDefault TTL 3600s. An expired capability is refused on presentation
sessionBound to the interaction, and destroyed when it dissolves

The sequence is: semantic authorisation decides whether; a capability records what; deterministic execution enforces it. The judgement is made once, by the layer able to reason about purpose, and everything downstream is a mechanical check.

5.1 What the coordinator does

  1. Admission — authenticates the connection, checks the agent is neither rejected nor revoked, and verifies the credential is entitled to the claimed agent_id.
  2. Intent processing — admits or refuses the intent (IBAC point 1), then decomposes it into sub-intents.
  3. Discovery — semantic matching against the capability registry.
  4. Negotiation — collects offers, evaluates eligibility (point 2), composes a plan (point 3).
  5. Execution — authorises each step (point 4), dispatches, supervises, scores.
  6. Validation — optionally has a nominated agent validate the result, with bounded renegotiation.
  7. Dissolution — invalidates the context and archives the audit record.

5.2 Transport independence

The coordination logic never touches the wire — it asks a transport for a peer and sends an envelope. Two transports ship:

TransportUse
WSServerAgents connect over WebSocket from anywhere — separate processes, containers, machines, languages.
LocalTransportAgents attach in-process. No port, no socket, no serialisation. Lets the coordinator run as a library inside an application that already owns a process.

Envelopes are deep-copied across the in-process boundary. A socket hands each side its own object for free; skipping the copy would let code pass locally and misbehave over a network, which is worse than having no local transport at all.

5.3 Agent-side ergonomics

# Python
class Weather(BaseAgent):
    def capabilities(self):
        return [AgentCapability(capability_id="forecast",
                                 required_scopes=["weather:read"])]

    async def execute_task(self, payload, context):
        return {"forecast": await lookup(payload["city"])}

await Weather(agent_id="weather-01").run_forever()

That is the entire surface. There is no router to configure and no other agent to point at: the coordinator discovers forecast from the registration and addresses it when an intent calls for it. The SDK handles registration per connection, jittered reconnection, per-session cancellation, and refusing to execute before execute arrives.

5.4 Security posture

ControlBehaviour
Agent authenticationBearer credential on the WebSocket upgrade. OIDC verification when AGBUS_OIDC_ISSUER is set; refused at handshake if missing or invalid.
Development modeAdmitted without a credential but carrying no identity, so identity_verified is false everywhere it matters.
EntitlementAn agent_id binds to the first authenticated subject that registers it. Only that subject may claim it afterwards; a connection can never overwrite a binding.
RevocationEnforced in ephemeral mode too — revocation escapable by reconnecting differently is a suggestion.
AuditEvery coordinator decision is recorded with actor, target, severity and reason.
06

Evidence

A specification is a claim. This section is what has actually been demonstrated, and it is the material worth leading with in a technical argument.

6.1 An independent implementation, from the document alone

A TypeScript agent client was written from the specification and the published JSON Schemas, without reference to the Python implementation. That constraint is the point: anything the document leaves out shows up as a guess.

Result: fully conformant, zero advisory warnings, in roughly 300 lines over one runtime dependency. The exercise also surfaced four gaps, three of which were genuine defects now fixed in the specification:

  1. How a credential is carried was undefined. §12 required authentication and the envelope had oidc_subject, but nothing said how a token reaches the coordinator. Now specified as Authorization: Bearer on the upgrade request.
  2. That the coordinator relays intent to agents was only inferable from the fact that an agent could not otherwise know what to offer against. Now stated.
  3. Dissolution mid-execution was undefined — whether to still send complete. Two conformant implementations could have behaved differently. Now stated.
  4. An ordering trap in the phrasing. “An agent joins by sending register and waiting for registered” reads as send, then wait — which drops the acknowledgement that arrives in between. The specification now says an agent must be receiving before it registers.

6.2 A conformance suite

Twelve graded requirements, protocol-only, so it does not care what language an agent is written in. MUST failures break conformance; SHOULD failures warn.

RequirementLevelChecks
LIP-REG-001MUSTregister is the first message on a connection
LIP-REG-002MUSTThe register payload carries an agent_id and validates
LIP-REG-003SHOULDAt least one capability is declared
LIP-INT-001MUSTA matching intent produces an offer
LIP-EXE-001MUSTNo execution before execute arrives
LIP-EXE-002MUSTcomplete is emitted when execution ends
LIP-DIS-001MUSTWork stops on dissolve
LIP-MSG-001MUSTEvery message is a valid envelope
LIP-MSG-002MUSTEach payload matches the schema for its type
LIP-MSG-003MUSTOnly defined performatives are used
LIP-VER-001MUSTEvery message carries a protocol_version
LIP-ACK-001SHOULDServing continues when registered never arrives
Why this matters more than the pass

The suite is also run against deliberately broken agents, each violating exactly the requirement it covers. A conformance suite everything passes certifies nothing.

6.3 A working end-to-end run

One sentence — “a storm has closed the Port of Rotterdam; reroute our refrigerated pharmaceuticals from Hamburg to Madrid within five days, and confirm cold-chain warehouse space” — decomposed into sub-intents, discovered four agents that were never wired to each other, collected and evaluated their offers, composed a six-step plan, paused at a human approval gate, executed, validated, scored each agent, and dissolved. Elapsed: 47 seconds.

No agent in that run knew about any other. Adding a fifth would have required registering it, and editing nothing.

07

Where LIP sits

The most common misreading is that LIP competes with MCP or A2A. It does not, and arguing that it does is the fastest way to lose a technical audience.

ProtocolAnswersRelationship to LIP
MCPHow does a model call a tool?Complementary and below. An MCP server is a capability an agent can offer. agentic-bus ships an MCP bridge for exactly this.
A2AHow do two agents exchange messages?Complementary and below. A2A is transport and framing between peers; LIP is what the messages mean and who decides.
ACPHow are agents described and discovered?Overlapping at discovery. LIP adds negotiation, authorisation and dissolution around it.
LIPWho should do this, may they, under what terms, and what happens afterwards?—
The position to argue

MCP won tools. A2A is winning messaging. Neither expresses purpose, delegation, revocation or provenance — and independent analysis of the agent-protocol landscape identifies exactly that gap. LIP is a governance and coordination layer that sits above them, not a replacement for either. The right posture is “we layer on A2A”, not “we compete with A2A”.

08

Objections, answered

Including the ones that are correct. A defence that has no concessions in it is not credible to the audience you most want to convince.

This is a language model deciding access control. That is disqualifying.

It would be, if the model could grant. It cannot. Decisions from three layers are combined by taking the strictest, and the two deterministic layers run regardless — one of which reads only coordinator-derived facts and never invokes a model at all. The semantic layer can turn ALLOW into DENY; the ordering makes the reverse impossible.

And when the model is unreachable, the answer is DENY, not “continue without it”.

Without a fixed contract, what stops the system hallucinating one?

Today, honestly: not enough. A plan is composed by a model over declared capabilities, and nothing yet requires every planned step to name a capability that was actually offered, or checks that an artifact matches the output_schema its offer promised.

This is a known gap with a proposal against it — RFC 0002, Capability Authority — which constrains composition to the capabilities admitted in this session, validates artifacts against their declared schema, and answers a violation with the valid alternatives. The authority is derived from this session's offers, held by nobody, and dissolved with the session: the interface stays ephemeral, it just stops being imaginary.

Negotiating every interaction is far too slow.

Correct, for the wrong workload. LIP is a coordination protocol, not a data path. Discovery, planning and semantic authorisation cost seconds, and no argument makes that acceptable in a hot loop called thousands of times a second.

It is the right trade when the alternative is a human deciding, or a connector being written. Use it where the work is coarse-grained and the coordination is the hard part — and call the deterministic path directly where it is not.

If plans are composed at runtime, debugging is impossible.

Only if nothing is recorded. Every decision is auditable: the intent, its decomposition and rationale, which agents were discovered and why, each offer, every IBAC evaluation with the layer that decided and its reason, each execution step with latency and score, and the dissolution. A completed session is reconstructible from its archive.

The honest form of this objection is different and worth conceding: reproducibility is harder than in a static system, because the same intent may produce a different plan tomorrow. Determinism was traded for adaptability deliberately.

This is a workflow engine with extra steps.

The distinguishing test is what happens when you add a participant. In a workflow engine, adding a step means editing the workflow — the topology is authored. Under LIP, an agent registers its capabilities and becomes discoverable; nothing else changes, and no existing agent is modified.

The second test is what happens when a step fails. A workflow retries or fails the run. A coordinator can renegotiate — bounded, three rounds — because the plan was never the authority; the intent was.

Who maintains this? It looks like one company's internal protocol.

Fair, and currently accurate. What exists to answer it: an open specification with an RFC process, published JSON Schemas with CI enforcing that implementation and schema cannot drift, a language-agnostic conformance suite, and two independent client implementations — one written from the document alone, precisely to prove the document is sufficient.

What does not yet exist is adoption outside its origin. That is the real gap, and it should be conceded rather than argued around.

Ephemeral interfaces mean losing type safety.

The performative set is closed and the envelope is schema-validated — in TypeScript MessageType is a finite union the compiler enforces, and payloads validate against published JSON Schemas on every message. What is not statically typed is the relationship between two agents, because that relationship did not exist until the interaction started.

The trade is real: static typing at the boundary, runtime validation across it.

9.2 Known gaps

Stating these first is more persuasive than being asked about them. Three that appeared here at 0.2.0 — no capability authority, no tenant isolation on the coordination path, and no enforcement of a granted scope — closed in 0.3.0. The ones below did not.

  • A scope is still a statement of intent. Grants are catalogued, bound by an administrator and checked at the point of use — but the check lives inside the agent's process. It stops an agent whose model was talked into exceeding its authority; it does not stop one whose code is hostile, and nothing running in that process could. What the coordinator gets is detection with attribution, which is what makes revocation mean something.
  • An agent that under-declares is not caught. Enforcement acts on what an agent said it needs. Declaring less passes.
  • Sequential execution only. No parallel fan-out with synthesis.
  • No cost or token budget abstraction. Negotiation and renegotiation are bounded by round count, not spend.
  • Adoption. One production lineage, no external users yet.

9.3 What would change the argument

The strongest thing that could happen to this protocol is not another feature. It is a second organisation depending on it, because a framework with one user invents requirements while a framework with users discovers them. Everything in section 6 exists to make that step cheap for whoever takes it.
